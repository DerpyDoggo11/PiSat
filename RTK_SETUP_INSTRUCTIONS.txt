================================================================================
 PiSat  --  Dual-GPS rover  --  FULL SETUP & WIRING GUIDE
================================================================================
 CURRENT SETUP: TWO PiSats ride ON THE ROVER, each with its own GPS antenna.
   - MAIN PiSat: motors + GNSS + pathfinding. This is the rover's brain and the
     WiFi access point. It follows the waypoint path and drives the motors.
   - CLIENT PiSat: GNSS only (no motors). It streams its position ($GP2) to the
     main PiSat over WiFi.
 The main PiSat AVERAGES both GPS fixes (its own + the client's) to beat down
 single-receiver noise, then follows the path and streams telemetry to a
 Processing sketch on your laptop. NO fixed base station is required.

 OPTIONAL: a fixed BASE PiSat still exists for position-domain differential
 ($PSDG) RTK -- see sec. 13. It is NOT part of the dual-GPS rover setup and is
 off by default (on single-band L1 it usually adds noise). Ignore it unless you
 specifically want differential corrections.

 Everything in this guide matches the firmware in this repo. Every PiSat pairs an
 RP2350 with an external ESP32-C3 Super Mini:
   RP2350 Firmware/        -> every PiSat's brain. envs: "main" (rover, default),
                              "client" (2nd GPS-only PiSat), "base" (optional RTK base).
   ESP32 Firmware/         -> every PiSat's ESP32-C3 WiFi bridge. envs: "main"
                              (rover, default), "main_ntrip" (NTRIP), "client"
                              (2nd-GPS uplink), "base" (optional base uplink).
                              [src/bridge_sta.cpp serves both client + base.]
   Processing/PiSatRTK/    -> the laptop visualiser

 So the dual-GPS rover = MAIN PiSat (RP2350 "main" + ESP32 "main") + CLIENT PiSat
 (RP2350 "client" + ESP32 "client"). Flash all four. The base envs are optional.

================================================================================
 0. WHAT YOU NEED
================================================================================
  - 2x assembled PiSat boards, each with a GPS antenna on the SMA connector.
    BOTH ride on the rover: one is the MAIN PiSat (motors), one is the CLIENT
    PiSat (2nd GPS, no motors).
    NOTE: the PiSat's ONBOARD ESP32-C3 is NOT populated on these boards, and it
    is not needed. All WiFi runs on the EXTERNAL ESP32-C3 super minis (which
    have their own PCB antennas). The PiSat's 2.4 GHz WiFi antenna connector is
    therefore unused -- you don't need to fit it. Nothing is ever flashed
    "through" the PiSat; each external C3 and each PiSat RP2350 is flashed over
    its own USB port.
  - 2x ESP32-C3 Super Mini   (one per PiSat: MAIN = AP + bridge, CLIENT = uplink)
  - 2x ZS-X111H (a.k.a. ZS-X11H) brushless motor controllers + 2 BLDC motors +
    a motor battery (6-60 V per the driver). Optional for bench testing -- the
    whole GPS/RTK/telemetry chain works with no motors connected.
  - Dupont wires, common ground between each PiSat and its ESP32.
  - A laptop with Processing 4.x installed, with WiFi.
  - USB cables to flash each board.

  Logic levels: RP2350, ESP32 and ESP32-C3 GPIO are all 3.3 V. You can wire them
  directly -- no level shifter needed.

================================================================================
 1. HOW IT WORKS HERE  (dual-GPS averaging)
================================================================================
  A single L1 GPS receiver jitters by a few metres from multipath and noise, and
  that noise is largely INDEPENDENT between two receivers. So this rover carries
  TWO PiSats, each with its own GPS, and averages their fixes -- the common
  signal survives, the independent noise partly cancels.

  Data flow, all onboard the rover:
    - MAIN PiSat: reads its own GNSS. It is also the WiFi access point and runs
      the pathfinding + motors.
    - CLIENT PiSat: reads its own GNSS and sends its position 5x/second as a
      $GP2 sentence -> its ESP32-C3 -> WiFi -> the MAIN PiSat's command port :8889.
    - MAIN PiSat RP2350 AVERAGES the two fixes (inverse-HDOP weighted; it rejects
      a client fix that is stale or that disagrees with its own by a big margin,
      and it also rejects single-cycle GPS "jumps" beyond what the rover's speed
      allows). The averaged, filtered position drives the path following.

  WHO DOES WHAT: the MAIN PiSat RP2350 is the brain -- parses its GNSS, fuses the
  2nd GPS, follows the waypoint path, and DRIVES the two ZS-X111H motor
  controllers on its own breakout GPIO. Its ESP32-C3 carries WiFi only (hosts
  the AP, telemetry out, $GP2/commands in). The CLIENT PiSat has no motors and
  no pathfinding -- it just publishes its position.

  >> Accuracy note: the PiSat GNSS is a Lantronix PNT-SG3FS (ST Teseo III), a
     SINGLE-FREQUENCY (L1) module. Averaging two of them cuts jitter but does not
     make it a dual-band ZED-F9P -- expect sub-few-metre, smoothed positioning,
     not centimetre RTK. For a true correction path (a fixed BASE PiSat, or NTRIP)
     see sec. 13; those are optional and OFF by default (on L1 the local base
     often adds more noise than it removes -- averaging is the better default).

 2. SYSTEM / DATA-FLOW DIAGRAM
================================================================================

   Both PiSats ride on the rover. The CLIENT sends its GPS to the MAIN; the MAIN
   averages, drives, and talks to the laptop.

   CLIENT PiSat (2nd GPS, no motors)        MAIN PiSat (motors + brain)
   ---------------------------------        ---------------------------
   [GPS antenna]                            [GPS antenna]
        |                                        |
   +----------+                     +----------+  GNSS UART (both ways)
   | PiSat    | GNSS UART           | PiSat    |  Teseo III
   | (CLIENT) | Teseo III           | (MAIN)   |  BRAIN: GNSS + 2-GPS averaging
   | RP2350   |---> $GP2 pos        | RP2350   |  + pathfinding + motors
   +----------+                     +----+-----+---------+-------------------+
        | GP0(TX)                GP0(TX) |    | GP1(RX)  | J5/J6 breakout:
        v                     telemetry  |    | $GP2 in  | 2x PWM/DIR/BRAKE+M
   +--------------+           +----------+    +--------+ v  ("ESP32" header UART)
   | ESP32-C3     | WiFi STA  | ESP32-C3 SM (WiFi BRIDGE)| +------------------+
   | Super Mini   |==========>| SoftAP "PiSat-RTK"       | | 2x ZS-X111H BLDC |
   | (uplink)     | TCP :8889 | :8889 $GP2/cmds (->RP2350)| |  -> 2 wheels     |
   +--------------+  ($GP2)   | :8888 telemetry (<-RP2350)| +------------------+
                              +-------------+------------+
                                    ^       | TCP :8888 telemetry
                       WiFi (join   |       v
                       PiSat-RTK)  +-----------------+
                                   | Laptop / Processing
                                   +-----------------+

   The MAIN PiSat (RP2350) is the brain: fuses its own GPS with the client's
   $GP2, follows the path, and drives the two ZS-X111H controllers on its own
   breakout GPIO. Its ESP32-C3 is only the access point + a transparent
   WiFi<->UART bridge: $GP2/commands in, telemetry out to Processing.
   (An OPTIONAL fixed BASE PiSat can also push $PSDG on :2101 -- see sec. 13.)

================================================================================
 3. PiSat BOARD PINOUT REFERENCE
================================================================================
 (Source: schematic.png, wiring.png, and RP2350 Firmware/src/pins.h. The RP2350
  is the hub: it owns the GNSS, the onboard ESP32-C3, and all breakout headers.)

 3.1  RP2350  <->  onboard GNSS (Teseo III / PNT-SG3FS)   -- already routed on PCB
      RP2350 GP4  = UART TX  -> GNSS UART_RX
      RP2350 GP5  = UART RX  <- GNSS UART_TX     (Serial2 @ 9600 baud default)
      RP2350 GP6  = GNSS NRESET
      RP2350 GP7  = GNSS WAKEUP
      RP2350 GP8  = GNSS PPS (1 pulse/sec, rising-edge IRQ)
      RP2350 GP9  = GNSS ANTOFF (antenna power / LNA enable, active behaviour
                    in firmware: LOW = antenna on)
      The GPS RF path: SMA connector -> RF_IN -> module. Put the GPS antenna
      with clear sky view; keep it away from the WiFi antenna.

 3.2  RP2350  <->  onboard "ESP32" header  -- the C3 footprint is NOT POPULATED,
      so this hardware UART (Serial1) is REUSED as the external-C3 link:
      RP2350 GP0 = TX (-> external C3 RX)   RP2350 GP2 = (was C3 EN) unused
      RP2350 GP1 = RX (<- external C3 TX)   RP2350 GP3 = (was C3 BOOT) unused
      This is the firmware default (PISAT_LINK_HW_UART = 1). It is the same
      6-pin "ESP32" header used for power/GND (sec. 3.5).

 3.3  Status / HMI
      RP2350 GP10 = LED A (status)   active-LOW
      RP2350 GP11 = LED B (status)   active-LOW
      RP2350 GP25 = Buzzer

 3.4  Breakout headers (where you attach the external ESP32-C3 and the motors)
      J4  (Conn_01x03, "GPIO 27/28/29"):  GP27, GP28, GP29  -- ADC-capable, spare
      J5  (Conn_01x05, "GPIO 20-24"):      GP20, GP21, GP22, GP23, GP24
           ^ ROVER: RIGHT-wheel ZS-X111H signals (GP24 spare):
               GP20 = RIGHT PWM(P)   GP21 = RIGHT SPEED(M fb)   GP22 = RIGHT BRAKE
               GP23 = RIGHT DIR(ZF)  GP24 = spare
      J6  (Conn_01x05):                    GP12, GP13, GP14, GP15, GP19
           ^ ROVER: LEFT-wheel ZS-X111H signals (GP14 spare). GP12/GP13 are free
             because the C3 link is on the "ESP32" header (GP0/GP1):
               GP12 = LEFT ROTATION(ZF)   GP13 = LEFT BRAKE   GP14 = spare
               GP15 = LEFT PWM(P)         GP19 = LEFT SPEED(M fb)
           NOTE: confirm which physical pin is GP12 vs GP13 on your silkscreen /
           the KiCad netlist. The firmware (pins.h: PIN_J6[5]={12,13,14,15,19})
           treats them as J6 positions 1..5.

 3.5  Debug / power / link pads
      "RP2350" header: 3V3, GND, CLK(SWCLK), DIO(SWDIO), RUN
      "ESP32"  header: RX, TX, EN, BOOT, 3V3, GND
         ^ This is now the LINK header to the external C3. Its two data pins are
           RP2350 GP0 (TX, drives the C3 RX) and GP1 (RX, reads the C3 TX), plus
           3V3 + GND to power/ground the C3. The silk "RX"/"TX" are named for the
           absent onboard C3, so don't take them at face value -- if data doesn't
           flow, swap the two signal wires. EN/BOOT are unused.

 3.6  Power
      RP2350 GP26 = VBAT ADC (2:1 divider, 3.3 V ref) -> battery voltage
      18650 cell -> onboard charger (USB-C) + 3.3 V regulator. ~12 h runtime.

================================================================================
 4. WIRING A:  ROVER  --  PiSat <-> C3 bridge, and PiSat <-> two ZS-X111H
================================================================================
 The rover PiSat (RP2350) is the brain and drives the motors from its OWN
 breakout GPIO. The ESP32-C3 Super Mini is only a WiFi bridge. So there are two
 wiring groups: the C3<->PiSat link, and the PiSat<->motors.

 4.1  PiSat rover  <->  C3 Super Mini  (UART link, common GND):
   Use the PiSat's onboard "ESP32" header -- it is the RP2350's real hardware
   UART (Serial1), free because the onboard C3 is not populated. (This is the
   firmware default; it also frees J6 GP12/GP13.)
   PiSat (ROVER) "ESP32" header  ESP32-C3 Super Mini    meaning
   ----------------------------  -------------------    -------
   GP0  (TX, header)  ---->  GPIO 20 (RX pad)           telemetry text out
   GP1  (RX, header)  <----  GPIO 21 (TX pad)           RTCM3 corrections in
   3V3  (header)      ---->  3V3 pin (power the C3)      optional
   GND  (header)      -----  GND                         common ground
   - The header's EN/BOOT pins are unused -- leave them open.
   - Electrically: GP0 is the RP2350 TX (drives the C3 RX); GP1 is the RP2350 RX
     (reads the C3 TX). If telemetry doesn't flow, swap the two data wires (a
     UART TX/RX swap is harmless to try).
   - Link baud 115200 (both sides set).
   - Prefer the J6 soft-UART on GP12(TX)/GP13(RX) instead? Rebuild the rover with
     -DPISAT_LINK_HW_UART=0 and wire those pins as the previous revision did.

 4.2  PiSat rover breakout  <->  two ZS-X111H controllers:
   The motors connect ONLY to the PiSat. Four wires per wheel: P (PWM speed, an
   output), ZF (rotation/direction, output), BRAKE (output), and M (speed
   feedback pulse, an INPUT the PiSat counts). Because the C3 link now uses the
   "ESP32" header, GP12/GP13 are free for motors.

   Wheel  Signal              PiSat GPIO      ZS-X111H terminal
   -----  ------              ----------      -----------------
   RIGHT  pwm                 GP20 (J5)  ->   P     (PWM speed input)   [driver #1]
   RIGHT  speed feedback      GP21 (J5)  <-   M     (FG / pulse output) [driver #1]
   RIGHT  brake               GP22 (J5)  ->   BRAKE                     [driver #1]
   RIGHT  rotation (dir)      GP23 (J5)  ->   ZF    (direction)         [driver #1]
   LEFT   pwm                 GP15 (J6)  ->   P     (PWM speed input)   [driver #2]
   LEFT   speed feedback      GP19 (J6)  <-   M     (FG / pulse output) [driver #2]
   LEFT   brake               GP13 (J6)  ->   BRAKE                     [driver #2]
   LEFT   rotation (dir)      GP12 (J6)  ->   ZF    (direction)         [driver #2]
   Signal ground (both)       GND (pad)  ->   G     (each driver's P/G header)

   >> LEFT brake on GP13, LEFT rotation on GP12.
      NOTE: these LEFT pins only work with the default HW-UART link. If you
      rebuild with -DPISAT_LINK_HW_UART=0, GP12/GP13 revert to the link and the
      firmware refuses to compile until you move LEFT brake/rotation.

   Driver-to-motor (NOT through the PiSat):
     B+ / B-      -> motor battery (6-60 V). Do NOT power the PiSat from B+.
     MA / MB / MC -> motor phase wires
     H            -> motor hall-sensor connector (sensored motors)

   Motor-supply ground and the PiSat signal ground MUST be tied together
   (common GND) so the PWM/DIR/BRAKE levels are referenced correctly.

   Speed-feedback (M) caveat: the firmware enables an internal pull-up and counts
   falling edges, which suits an open-collector M output. If your ZS-X111H drives
   M as a push-pull 5 V signal, drop it to 3.3 V (divider or level shifter) before
   GP21/GP19. It is optional -- unwired, wheel-speed just reads 0 Hz.

 4.3  IMPORTANT ZS-X111H setup (do this or the P input is ignored):
   - PWM MODE: these boards ship set up for their onboard potentiometer. To take
     an external PWM on P/G you must enable the board's "short interface" (the
     solder short / jumper next to the P/G header) AND turn the onboard speed
     potentiometer to MINIMUM. Then P/G accepts PWM: amplitude 2.5-5 V,
     frequency 50 Hz-20 kHz. (The firmware's analogWrite PWM ~1 kHz is in range.)
   - DIRECTION (ZF) and BRAKE are level inputs; BRAKE engages on a HIGH (~5 V).
   - 3.3 V LOGIC CAVEAT: the PiSat RP2350 drives 3.3 V. PWM (min 2.5 V) works
     fine. DIR and BRAKE expect ~5 V high -- 3.3 V USUALLY triggers them, but if
     a wheel won't change direction or brake, add a simple NPN/MOSFET level
     shifter (or a logic-level converter) on ZF/BRAKE. If a wheel spins the WRONG
     way, just flip DIR_R_FORWARD / DIR_L_FORWARD in RP2350 Firmware/src/main.cpp
     -- no rewiring.
   - The M (speed-feedback / FG pulse) output is optional and NOT used by the
     control loop; leave it unconnected.

   Power the C3 from its own USB while bench-testing, or from the PiSat "ESP32"
   header 3V3/GND pads on the robot -- always keeping a common ground. The motor
   drivers run from their own battery (B+/B-), never from the PiSat rail.

================================================================================
 5. WIRING B:  CLIENT (2nd GPS) PiSat  <->  ESP32-C3 Super Mini   (uplink)
================================================================================
 The client PiSat runs the RP2350 "client" firmware: GNSS only, no motors. It
 streams its position ($GP2) out on the onboard "ESP32" header's TX (GP0). Its
 C3 (ESP32 "client" firmware) reads it and forwards it over WiFi to the MAIN
 rover. One-way (client->C3). Wiring is IDENTICAL to the main rover's C3 link.

   PiSat (CLIENT) "ESP32" header  ESP32-C3 Super Mini           meaning
   ---------------------------    -------------------           -------
   GP0  (TX, header)     ---->  GPIO 20 (RX)                 $GP2 position out
   3V3  (header)         ---->  3V3 pin (power the C3)       optional
   GND  (header)         -----  GND                          REQUIRED common ground

   (No return wire needed. GPIO 21 on the C3 is an unused spare. Build the client
    with -DPISAT_LINK_HW_UART=0 to stream on J6 GP12 instead.)

   Power the C3 from its own USB, or from the client PiSat's 3V3/GND pads. Give
   the client's GPS antenna its own clear sky view, ideally spaced from the main
   antenna so their multipath is independent -- that is what makes averaging help.

 (Same wiring serves an OPTIONAL fixed BASE PiSat: flash RP2350 "base" + ESP32
  "base" instead; its C3 pushes $PSDG on :2101. See sec. 13. Not needed for the
  dual-GPS rover.)

 6. INSTALLING THE TOOLCHAIN (PlatformIO)
================================================================================
  1. Install VS Code, then the "PlatformIO IDE" extension. (Or use the CLI:
     `pip install platformio`.)
  2. First build will auto-download the toolchains. The RP2350 uses the
     earlephilhower arduino-pico core (already pinned in its platformio.ini);
     the ESP32s use the espressif32 platform.

  In the commands below, `pio` is the PlatformIO CLI. In VS Code you can instead
  pick the environment in the status bar and hit Build/Upload.

================================================================================
 7. FLASHING THE FIRMWARES
================================================================================
  Flash each board over its own USB. The dual-GPS rover needs all four (a-d).

  (a) MAIN PiSat -- RP2350 rover firmware:
        cd "RP2350 Firmware"
        pio run -e main -t upload
      Hold BOOTSEL if needed for the first flash (RP2350 mass-storage mode).

  (b) MAIN ESP32-C3 Super Mini -- the WiFi bridge + access point:
        cd "ESP32 Firmware"
        pio run -e main -t upload

  (c) CLIENT PiSat -- RP2350 2nd-GPS firmware:
        cd "RP2350 Firmware"
        pio run -e client -t upload
      (Same code base, -DPISAT_CLIENT selected by the "client" env.)

  (d) CLIENT ESP32-C3 Super Mini -- the 2nd-GPS uplink:
        cd "ESP32 Firmware"
        pio run -e client -t upload

  (e) OPTIONAL -- fixed BASE PiSat (only if you want $PSDG differential, sec. 13):
        cd "RP2350 Firmware" && pio run -e base -t upload   # RP2350
        cd "ESP32 Firmware"  && pio run -e base -t upload   # its ESP32-C3

  (If a C3 super mini won't enter download mode: hold BOOT, tap RST, release BOOT,
   then upload.)

  All boards flash over their OWN USB ports -- nothing goes "through" the PiSat.
  The onboard ESP32-C3 is not populated; all WiFi runs on the external C3s.

================================================================================
 8. CONFIGURING IT
================================================================================
 8.1  WiFi network (must match on the MAIN C3 and the CLIENT C3):
        ESP32 Firmware/src/main.cpp        -> AP_SSID / AP_PASS   (MAIN, the AP)
        ESP32 Firmware/src/bridge_sta.cpp  -> ROVER_SSID / ROVER_PASS (client + base)
      Defaults: SSID "PiSat-RTK", password "pisat-rtk-1234". The MAIN C3 is the
      access point at 192.168.4.1. The client C3, your laptop (and an optional
      base C3) all join it.

 8.2  The rover's path + boundary -- NO longer compiled in. Draw them in the
      PiSatPlanner sketch over satellite imagery and the runtime sketch pushes
      them to the rover over WiFi at runtime (see sec. 14). The rover stores them
      in RAM ($WPT/$BND); no reflash to change a path. (Firmware default: empty
      until the visualiser sends one.)

 8.3  Drive tuning (RP2350 Firmware/src/main.cpp, ROVER branch): PID steering
        gains KP/KI/KD, plus MAX_PWM, WAYPOINT_RADIUS_M, MIN_SPEED_FOR_COURSE,
        PIVOT_DEG, and position smoothing SMOOTH_MIN/MAX. Data filtering:
        GPS_JUMP_M (outlier reject), GP2_MAX_DISAGREE_M / GP2_TIMEOUT_MS (2nd-GPS
        averaging). Direction/brake polarity: DIR_R_FORWARD, DIR_L_FORWARD, BRAKE_ON.
      Pathfinding is go-to-point: the rover heads for waypoint 0 first, marks it
      reached within WAYPOINT_RADIUS_M, then advances through the rest in order.
      NOTE: motor output starts conservative (MAX_PWM = 40 / 255). Raise it once
      you trust the steering. "hold" on the console brakes; "auto" resumes the
      path; WASD manual control is in the runtime sketch (sec. 14). Harmless with
      no motors wired.

 8.4  OPTIONAL -- base differential reference (RP2350 Firmware/src/main.cpp, BASE
        branch). Only relevant if you run a fixed base (sec. 13); NOT used by the
        dual-GPS rover.
        The base runs POSITION-DOMAIN DIFFERENTIAL (not RTCM3 -- see sec. 13). It
        needs a reference position to measure its error against:
          - Default = SURVEY-IN: after its first fix it averages its own position
            for SURVEY_SAMPLES seconds (~60 s), locks that as the reference, then
            streams $PSDG corrections. Best for repeatable RELATIVE accuracy.
            Re-run anytime with the "survey" console command.
          - KNOWN point: build the base with -DBASE_REF_LAT=.. -DBASE_REF_LON=..
            (decimal degrees) to skip survey-in and use a surveyed coordinate.
        Watch it on the base console: "gps" for sats/fix, "stat" for survey
        progress / ref lock / corrections-sent count.

================================================================================
 9. BRING-UP / OPERATING SEQUENCE
================================================================================
  1. Power the MAIN PiSat + its C3 bridge, outdoors with an open-sky GPS view.
     The C3 brings up the "PiSat-RTK" SoftAP (USB-serial prints the AP IP +
     "telemetry :8888 command :8889"). The RP2350 USB-serial prints
     "=== PiSat RTK ROVER ===". Let its GPS get a fix.
  2. Power the CLIENT PiSat + its C3, also open-sky. Its C3 auto-joins "PiSat-RTK"
     and connects to the MAIN C3's :8889 (client C3 serial prints "rover link up").
     Its RP2350 prints "=== PiSat CLIENT -- 2nd GPS ($GP2) ===" and, on the client
     console, "stat" shows a climbing "$GP2 sent" count once it has a fix.
  3. The MAIN PiSat now receives $GP2 and averages the two GPS. On the MAIN
     console, "stat" reflects the fused position; the Processing HUD shows a
     steadier fix than a single receiver.
  4. On your laptop, join "PiSat-RTK", then run the Processing sketch (sec. 10).
  5. To actually drive: wire the motors, push a path from the planner/visualiser,
     and power the rover in the field. It only drives when it has a fix and a
     valid path; it heads for waypoint 0 first, check-marks each waypoint as it
     reaches it, and stops at the last one (or if it leaves the BOUNDARY).

  (OPTIONAL fixed base: if you also run a base PiSat for $PSDG differential, set
   it up first per sec. 13 -- antenna FIXED and sky-open, survey-in ~60 s -- then
   enable it on the rover with the "diff on" console command. Off by default.)

================================================================================
 10. RUNNING THE PROCESSING TELEMETRY VISUALISER
================================================================================
  1. Open Processing/PiSatRTK/PiSatRTK.pde in Processing 4.x.
  2. Confirm ROVER_HOST = "192.168.4.1" and ROVER_PORT = 8888 at the top.
  3. Join the "PiSat-RTK" WiFi on the laptop.
  4. Press Run. The sketch:
       - connects to the rover's telemetry server (auto-reconnects if dropped),
       - draws the waypoint path, the optional boundary polygon, waypoint radii,
         and check-marks each waypoint green as the rover reaches it (amber =
         current target, blue = pending),
       - draws the rover moving along the path with a heading line (its GPS
         course) and a target-bearing line, plus a green breadcrumb trail,
       - shows a live HUD: fix quality (colour-coded: green = RTK fixed), lat/lon
         to 7 decimals, satellites, HDOP, speed, course, target waypoint + range,
         target bearing, cross-track heading error, path status, correction age
         (link health), and per-wheel PWM bars.
     The view auto-fits to the path + rover; a scale bar shows metres.

  SATELLITE BACKGROUND: the sketch overlays the path on Esri World Imagery
  (free, no API key). Press [s] to toggle it. Imagery needs INTERNET, which the
  "PiSat-RTK" access point does NOT provide -- so run Processing on a machine
  that can reach BOTH the rover and the internet at once (e.g. Ethernet for
  internet + WiFi on PiSat-RTK, or a second WiFi adapter). Without internet the
  map just doesn't load ("imagery needs internet"); telemetry and the path still
  work over the AP.

  No fix yet? The field stays empty until the rover reports its first valid fix
  (that sets the local-frame origin). The HUD still shows "NO FIX" and sat count.
  Still drifting a lot while stationary? That's L1 multipath -- the firmware
  already speed-adaptively smooths position (SMOOTH_MIN/MAX in the rover source);
  open sky helps most, and true cm stability needs carrier-phase RTK (sec. 13).

================================================================================
 11. TELEMETRY & CORRECTION PROTOCOL REFERENCE
================================================================================
 11.1  ROVER telemetry: RP2350 -> C3 bridge -> Processing. The RP2350 emits
        newline-terminated ASCII on the link; the C3 relays it verbatim to the
        Processing TCP client on :8888. Every line ends with an XOR checksum
        "<body>*HH" (XOR of all body chars, 2 hex digits) so Processing rejects a
        corrupted line instead of plotting a wild point.
        M,<maxPwm>,<wpRadius>,<wpCount>,<boundaryCount>     (path header, every 2 s)
        W,<i>,<lat>,<lon>                                   (each waypoint)
        B,<i>,<lat>,<lon>                                   (each boundary vertex)
        O,<lat>,<lon>                                       (local-frame origin)
        T,<ms>,<fixQual>,<lat>,<lon>,<course>,<speed>,<sats>,<hdop>,<seg>,
          <tgtBearing>,<hdgErr>,<done>,<corrAgeMs>,<pwmR>,<pwmL>,<spdHzR>,<spdHzL>,<mode>  (10 Hz)
        <lat>/<lon> are the DIFFERENTIALLY-CORRECTED position. <corrAgeMs> is the
        time since the last base correction (link health; the HUD shows "Corr age").
        fixQual is the GNSS's own quality; spdHzR/L = wheel-speed pulse Hz;
        <mode> = 0 auto / 1 manual / 2 hold. (Header resent every 2 s.)

 11.2  Corrections: BASE -> ROVER differential (position-domain DGPS). The base
        sends its position error once a second as a checksummed sentence:
          $PSDG,<valid>,<dLatDeg>,<dLonDeg>,<baseSats>,<baseFixQ>*hh
        (valid=1 once the base's reference is locked). The base C3 relays it over
        TCP :2101; the rover C3 passes it to the RP2350 (link RX), which parses it
        and SUBTRACTS the error from its own fix -- it is NOT fed into the GNSS.
        Stale after 5 s (then the rover falls back to its raw fix).

 11.3  Commands: VISUALISER -> ROVER, over TCP :8889 on the rover C3 (which
        forwards them to the RP2350 link; the RP2350 dispatches by prefix). All
        "<body>*HH" checksummed:
          $WPT,<i>,<n>,<lat>,<lon>   waypoint i of n  (path, pushed from the planner)
          $BND,<i>,<n>,<lat>,<lon>   boundary vertex i of n
          $MAN,<throttle>,<turn>     manual WASD drive, each in [-1,1] (10 Hz while held)
          $AUTO                      resume autonomous path-following
          $HOLD[,<0|1>]              brake hold (toggle or set)
          $SPD,<n>                   set MAX_PWM live (0-255)
          $PCLR                      clear path + boundary
        The base $PSDG (:2101) and these commands (:8889) share the rover link;
        the RP2350 tells them apart by sentence type.

 11.4  Second GPS: CLIENT -> ROVER, over TCP :8889 (same command server). The
        client PiSat sends its position 5x/second:
          $GP2,<lat>,<lon>,<hdop>,<sats>,<fixQ>*hh
        The rover averages it with its own fix (inverse-HDOP weighted; ignored if
        stale > GP2_TIMEOUT_MS or if the two disagree by > GP2_MAX_DISAGREE_M, in
        which case the lower-HDOP fix wins). Cuts independent L1 noise.

 12. TROUBLESHOOTING
================================================================================
  Rover C3 never says "base station connected":
    - Base C3 and rover C3 SSID/password must match exactly.
    - Rover C3 is the AP (192.168.4.1). Base C3 is STA. Check the base C3 USB
      serial for "joined" then "rover link up".
    - Keep both WiFi antennas in the open; 2.4 GHz hates metal enclosures.

  Motors don't move / wrong direction:
    - Do the ZS-X111H PWM-mode setup (sec. 4.3): short interface + pot to MIN.
    - Type "hold" on the RP2350 console to release the safety hold if engaged.
    - Wrong way? flip DIR_R_FORWARD / DIR_L_FORWARD (sec. 8.3). No fix or no path
      = motors stay stopped by design.
    - DIR/BRAKE not responding at 3.3 V? add a level shifter (sec. 4.3).

  Fix quality never rises above "GPS":
    - Corrections aren't reaching the GNSS. Check RTCM age in the HUD: if it says
      "no corrections", the WiFi/UART chain is broken (see wiring sec. 4/5).
    - The base needs a good sky view and must finish survey-in before it emits
      useful RTCM. Give it a few minutes, don't move it.
    - Confirm the base RP2350 "stat" shows rtcm frames increasing.
    - See section 13: the exact receiver-mode commands may need adjusting.

  Processing window is empty:
    - Laptop must be on "PiSat-RTK". Try http nothing -- it's raw TCP.
    - No origin until the first valid fix. Watch the HUD sat count.

  GNSS debug commands (type them on the RP2350 USB serial, ROVER and BASE both):
    gps  (or sats) -> friendly status: fix quality, satellites tracked, HDOP,
                      1PPS count, and -- before a fix -- how close it is and what
                      to check. Watch sats climb and HDOP fall as it converges.
    stat           -> one-line summary (adds RTCM frames on the base).
    nmea           -> toggle raw NMEA echo (see the actual $GxGGA/$GxRMC stream).
    gnss_reset     -> restart + reconfigure the module.
    ant on | ant off (rover) -> antenna bias power.

  How long to get a fix?
    Clear sky, good antenna: cold start ~30 s-2 min, warm ~20-30 s, hot a few s.
    Indoors/near a window it may take many minutes or never fix. If after a few
    minutes outdoors "gps" still shows 0 sats and "1pps 0", suspect the antenna
    or its bias (below), not the software.

  GNSS shows nothing / never tracks satellites:
    - Default GNSS baud is 9600 (pins.h GNSS_BAUD). Use "nmea" to echo raw NMEA
      and confirm the module is even talking.
    - "ant on", check the SMA antenna, "gnss_reset" to restart the module.
    - Bias-tee inductor NOT populated? That inductor feeds DC up the coax to
      power an ACTIVE antenna's LNA. Without it:
         * PASSIVE antenna (no LNA): still works -- you'll get a fix.
         * ACTIVE antenna (most GPS antennas, incl. the BOM ones): the LNA is
           unpowered -> little/no signal -> likely NO fix. Populate the inductor,
           or use a passive antenna. Test: with the antenna on and "ant on",
           measure DC on the SMA centre pin -- it should be ~3.3 V; 0 V means the
           bias path (that inductor) is open. "1pps 0" in "gps" is the same clue.

  RP2350 won't take new firmware:
    - Enter BOOTSEL (mass storage) and drag the UF2, or let PlatformIO reset it.

  Motors spin unexpectedly:
    - The rover only drives with a valid fix AND >=2 waypoints. Clear WAYPOINTS[]
      to keep it stationary while testing GPS/telemetry.

 13. THE GNSS-MODULE RTK CAVEAT   (READ THIS)
================================================================================
  The PiSat GNSS is a Lantronix PNT-SG3FS = ST Teseo III, SINGLE-FREQUENCY (L1),
  flash-based, multi-constellation (GPS/GLONASS/Galileo/BeiDou/QZSS). Confirmed
  from the datasheet: it supports DGPS corrections per RTCM 10402.3 and can be
  built/configured to output carrier-phase measurements for a host RTK algorithm.

  What that means for THIS project:
    - The transport in this firmware is correct and complete: base -> WiFi ->
      rover -> GNSS, both directions, framed and checksummed.
    - The exact commands that switch the Teseo III into "emit RTCM3 base output"
      and "consume RTCM3 as a rover" are ST $PSTM proprietary NMEA commands. The
      placeholders in gnss.cpp (Gnss::configureBase / configureRover) use the
      $PSTMSETPAR / $PSTMSAVEPAR scheme, but the exact PARAMETER IDs and the
      base-survey command name MUST be verified against YOUR module's:
          "Teseo III / Teseo-LIV3 Software Command / Firmware Reference"
      (ST doc; also see Lantronix's PNT-SG3FS material and ST's TESEO-SUITE PC
      tool, which can configure the module and show you the exact commands).
    - Once the receiver is genuinely in base/rover mode, everything else here
      works unchanged. If your particular firmware build does not expose on-chip
      RTK, you can still (a) get DGPS/sub-metre from RTCM, or (b) log raw
      measurements from both units and post-process with RTKLIB.
    - Realistic expectation for an L1 module: fast to sub-metre/DGPS; L1-only
      RTK "float/fixed" is possible with open sky and a good base but is slower
      and less robust than a dual-band (L1/L2) receiver like the u-blox ZED-F9P.

  FIELD FINDING (confirmed on hardware): the standard Teseo III firmware does
  NOT emit turnkey "RTCM3 base output" -- so the base shows `rtcm frames 0` and
  never sends corrections. Per ST UM2229, the Teseo III does RTCM3 *input* (rover
  corrections) and *raw-measurement* output (PSTMPVRAW, for HOST-side RTK); RTCM3
  *base* output is a Teseo-LIV4FM/Teseo VI (ME-firmware) feature. Check your
  module's firmware with the `ver` console command ($PSTMGETSWVER).

  WHAT THIS FIRMWARE DOES INSTEAD (implemented, default): POSITION-DOMAIN
  DIFFERENTIAL ("poor-man's DGPS"). The base surveys-in a reference, then sends
  its live position error ($PSDG) to the rover, which subtracts it. This uses
  both PiSats, needs no RTCM-base firmware / no PC / no internet, and gives
  meter-level, more-repeatable positioning (great for a path-follower). It is NOT
  centimeter RTK. See sec. 8.4 (base reference) and 11.2 ($PSDG). Accuracy is
  best when the two units are close (< a few km), both have good sky, and (since
  both already get SBAS/WAAS) it mainly removes residual/relative wander.

  UPGRADE PATHS for better/absolute accuracy:
    1. NTRIP: feed the rover RTCM3 from a nearby internet base (free CORS within
       ~10-30 km, or a service). The rover's GNSS accepts RTCM3 input directly.
       (Ask and this repo's rover C3 can be given an NTRIP client; note it would
       need internet, changing the rover from AP to a WiFi station.)
    2. Host RTK with RTKLIB (true cm/dm): enable raw measurements on BOTH PiSats
       ($PSTMSETPAR,1228,0x4000,1 ; $PSTMSAVEPAR ; $PSTMSRR), log them, and post-
       process / stream through RTKLIB on a PC.
    3. A Teseo base-capable firmware from ST (if available for the SG3FS).

  Realistic expectation for an L1 module: fast to sub-metre/DGPS with corrections;
  L1-only RTK float/fixed is possible with open sky but slower/less robust than a
  dual-band (L1/L2) receiver like the u-blox ZED-F9P.

  Sources:
    - Lantronix PNT-SG3FS datasheet (PDS-0021):
      https://www.mouser.com/pdfDocs/PDS-0021b-PNT-SG3FS-Datasheet.pdf
    - Lantronix PNT GNSS series: https://www.lantronix.com/products/pnt-gnss-series/
    - ZS-X11H controller pinout/specs (Cirkit Designer):
      https://docs.cirkitdesigner.com/component/4cf35777-c70f-44c9-9828-838f50915cea/zs-x11h-v2-350w-motor-controller
    - ZS-X11H Arduino wiring reference:
      https://github.com/aeoank/ZS-X11H-BLDC-motor-driver-arduino

 14. PLANNER, PID STEERING & MANUAL (WASD) CONTROL
================================================================================
 14.1  Plan the field (Processing/PiSatPlanner) -- needs internet:
     - Open PiSatPlanner.pde. It shows Esri satellite imagery. Pan (drag /
       arrows), zoom (wheel / + -) to your field.
     - [w] path mode: left-click to drop ordered waypoints. [b] boundary mode:
       left-click the corners of the keep-in polygon (>= 3 pts to be active).
     - [z] undo, [x] delete nearest, [c] clear mode, [C] clear all.
     - [s] SAVE: it auto-fits, downloads a crisp tile, and writes
           Processing/shared/project.jpg  +  project.pisat
       (imagery + bounds + waypoints + boundary). [l] reloads it.

 14.2  Run offline (Processing/PiSatRTK):
     - On start it loads Processing/shared/project.* if present -> uses the
       CACHED image (NO internet/fetching) and shows the path/boundary. Nothing
       is drawn until the rover's first fix (everything is drawn relative to the
       robot's local frame).
     - It also PUSHES the path + boundary to the rover over TCP :8889 once the
       command link is up ($WPT/$BND). No reflash needed to change a path -- edit
       in the planner, re-save, restart the runtime.
     - [m] toggles the map. If no project file exists it falls back to online
       imagery (needs internet, sec. 10).

 14.3  PID steering + smoothing (rover firmware, RP2350 Firmware/src/main.cpp):
     - Steering is now a PID on heading error (KP/KI/KD) feeding a differential
       drive (throttle +/- steer), with pivot-in-place beyond PIVOT_DEG. Tune
       KP/KI/KD if it weaves (lower KP / add a little KD) or is sluggish (raise
       KP). Position is speed-adaptively smoothed (SMOOTH_MIN/MAX).

 14.4  Manual control (WASD) in the runtime sketch:
     - W/S = forward/back, A/D = turn (differential). On-screen buttons
       (bottom-left) light up with the keys and are click-and-hold too.
     - [g] returns to autonomous path-following; [space] toggles brake HOLD.
     - The HUD shows the live mode (AUTO / MANUAL / HOLD) from telemetry.
     - Safety: the rover stops if no manual command arrives for 600 ms, and the
       boundary/low-voltage cutoffs still apply.

 15. NTRIP -- REAL RTCM3 CORRECTIONS FROM AN INTERNET BASE  (recommended RTK)
================================================================================
 Your GNSS already ACCEPTS RTCM3 input, so the easiest real RTK is to feed it
 corrections from an internet NTRIP caster (a base within ~10-30 km, or a paid
 service). No local base PiSat, no RTKLIB. The rover's GNSS then reports DGPS /
 RTK-float / RTK-fixed on-chip and the whole system uses that position.

 HOW IT WORKS: the rover C3 is flashed in NTRIP mode -- it joins your INTERNET
 WiFi (station), runs an NTRIP client, pulls RTCM3, and streams it to the RP2350,
 which forwards it into the GNSS. The RP2350 demuxes RTCM3 (-> GNSS) from the
 "$" commands automatically, so path/WASD still work on the same link.

     internet NTRIP caster --WiFi--> rover C3 (NTRIP client)
                                          |  RTCM3 over the link
                                          v
                                     rover RP2350 --> GNSS  (on-chip DGPS/RTK)

 SETUP:
   1. Get an NTRIP account + a nearby mountpoint. Free option: rtk2go.com
      (user = your email, pass = "none"); or a state/commercial CORS/VRS service.
   2. Edit ESP32 Firmware/src/main.cpp (top, the NTRIP CONFIG block):
        STA_SSID / STA_PASS   -> an internet WiFi (a phone hotspot works)
        NTRIP_HOST / _PORT / _MOUNT / _USER / _PASS   -> your caster + mountpoint
        NTRIP_GGA_LAT / _LON  -> a rough position (so VRS casters pick a base)
   3. Flash the rover C3 in NTRIP mode:  cd "ESP32 Firmware" && pio run -e main_ntrip -t upload
   4. Power up. The C3 serial prints "joined ... ip ..." and "NTRIP: streaming".
      Its `rtcm=` byte counter should climb. The rover "gps" fix quality should
      go GPS -> DGPS -> RTK float/fixed within a minute or two under open sky.

 TOPOLOGY NOTE: in NTRIP mode the rover C3 is a WiFi STATION, not the "PiSat-RTK"
 AP. So the laptop joins the SAME internet WiFi and Processing's ROVER_HOST must
 point at the rover's IP (printed on the C3 serial) or "pisat-rover.local". Bonus:
 the laptop then has internet, so the satellite background loads online too
 (or keep using the planner's cached offline imagery). The local base PiSat +
 $PSDG differential is not used in this mode; it stays available in the default
 [env:main] SoftAP build.

 CAVEAT: this is single-band L1 RTK via a possibly-distant base -- expect fast
 DGPS/sub-metre and, under good sky with a close base, L1 RTK float/fixed that
 is less robust than dual-band gear. Still the simplest path to real cm-class
 corrections with this hardware.

 (Even-more path: RTKLIB rtkrcv on a Raspberry Pi Zero 2 W using raw measurements
  -- `raw on` on both PiSats -- is the classic two-unit route but a bigger
  project; see sec. 13 for the raw-output caveat.)
